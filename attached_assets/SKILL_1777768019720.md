# Vibe Coding Skill

Vibe coding is the practice of building production-grade software by directing AI agents
through precise natural language, while you focus on architecture, product decisions, and
quality control — not syntax. This skill makes you the technical lead; the agent is your
engineering team.

---

## Core Philosophy

> **You are the architect. The agent is the builder. Never confuse the two roles.**

The #1 mistake vibe coders make is writing vague prompts and then micromanaging line-by-line
fixes. The better approach: invest 10 minutes writing a precise, structured prompt — then let
the agent run. A prompt that specifies file paths, function signatures, data shapes, and
acceptance criteria will outperform five rounds of "fix this error" every time.

**The Vibe Coding Mindset:**
- Think in systems, not files
- Specify outcomes, not steps
- Parallelize everything possible
- Trust the agent on implementation; own the architecture
- One checkpoint every 2–3 hours beats ten micro-reviews

## SECTION 1 — Prompt Engineering for AI Agents

### The Anatomy of a Great Agent Prompt

Every high-quality agent prompt has five parts. Missing any one degrades output quality
significantly:

```
[ROLE]       → Who is the agent in this context?
[CONTEXT]    → What already exists? What's the tech stack?
[TASK]       → What exactly needs to be built? Be specific.
[CONSTRAINTS]→ What rules must not be broken? (file paths, naming, patterns)
[ACCEPTANCE] → How will you know it worked? What should you see?
```

**Weak Prompt (avoid):**
```
Build a login page with authentication.
```

**Strong Prompt (use this pattern):**
```
You are building the authentication layer for a B2B SaaS called "LaunchFlow AI".

CONTEXT:
- Stack: Node.js + Express backend in /server, React + Vite frontend in /client
- Database: PostgreSQL with Drizzle ORM, schema already exists in /shared/schema.ts
- The users table has: id (uuid), replitUserId (varchar), email, displayName, avatarUrl

TASK:
Build Replit Auth (OIDC) middleware for the Express backend.
Create these endpoints:
  GET  /api/auth/user → return session user or 401
  POST /api/auth/logout → destroy session, return { success: true }
Protect all /api/* routes except /api/auth/user using requireAuth middleware.

CONSTRAINTS:
- Do NOT hardcode any secrets — read all keys from process.env
- Session store must use express-session with SESSION_SECRET env var
- Place middleware in /server/middleware/auth.ts (not inline in index.ts)
- Export requireAuth as a named export

ACCEPTANCE CRITERIA:
- Unauthenticated GET /api/projects returns 401
- Authenticated GET /api/auth/user returns { id, displayName, email, avatarUrl }
- Session persists across page reloads
Show me the middleware file and a test of each endpoint.
```

### Prompt Templates by Task Type

#### Database Schema Prompt
```
Create a PostgreSQL schema using Drizzle ORM in /shared/schema.ts.

TABLES NEEDED:
[table_name]: {
  [column]: [type + constraints]
}
Foreign keys: [table.column → table.column (onDelete behavior)]
Indexes: [column, reason]

ENUMS: [name: values[]]

Run: npx drizzle-kit push:pg
Confirm by showing the migration output and table list.
```

#### REST API Endpoint Prompt
```
Add these endpoints to /server/routes/[name].ts:

[METHOD] [path]
  Auth required: [yes/no]
  Body/Params: [shape]
  Logic: [numbered steps]
  Returns: [shape on success] | [error codes]

Requirements:
- Validate input with Zod before DB operations
- Wrap all DB calls in try/catch
- Return { error: string } on failure with appropriate status code
Register routes in /server/index.ts under /api prefix.
```

#### React Component Prompt
```
Build [ComponentName].tsx in /client/src/components/

Props interface:
  [prop]: [type] — [what it does]

Render:
  [Describe the visual layout and behavior in plain English]
  [Specify interactive states: hover, loading, error, empty]
  [Specify what happens on user actions]

Styling: Tailwind CSS only. Color scheme: [describe].
No external component libraries unless already installed.
Export as default export.
```

#### Background Agent / Async Job Prompt
```
Create /server/agents/[agentName].ts

Export: async function run[AgentName](jobId: string): Promise<void>

This function runs as a BACKGROUND TASK (never awaited by the caller).

Steps:
1. [Fetch inputs from DB]
2. [Call external API or AI model]
3. [Process response]
4. [Write results to DB]
5. [Update status field to "completed" or "error"]

Error handling:
- Wrap EVERYTHING in try/catch
- On error: update status to "error", log the error, NEVER throw
- Never let an unhandled rejection crash the server

The caller fires this with: run[AgentName](id).catch(console.error); // no await
```

## SECTION 2 — Parallel Execution Strategy

### Why Parallelism Wins Hackathons

Sequential development: build A → build B → build C → done in 12 hours.
Parallel development: build A + B + C simultaneously → done in 4 hours.

In Replit Agent 4 and similar tools, you can open multiple agent chat threads. Each thread
operates independently in an isolated environment. Use this to run frontend and backend
development simultaneously.

### The Dependency Graph Method

Before writing prompts, map what depends on what:

```
Step 1: Draw your dependency tree
─────────────────────────────────
         [DB Schema]          ← no dependencies, start here
        /           \
  [Backend API]  [Auth Layer]  ← depend on schema
       |               |
  [AI Agents]    [Frontend Shell]  ← depend on API contracts
       \               /
        [UI Data Wiring]  ← depends on both
              |
         [Polish + Deploy]  ← depends on everything

Step 2: Identify the parallelizable layers
──────────────────────────────────────────
Layer 0 (sequential): DB Schema + project bootstrap
Layer 1 (parallel):   Backend API  ‖  Frontend Shell  ‖  Auth
Layer 2 (parallel):   AI Agent A   ‖  AI Agent B      ‖  AI Agent C
Layer 3 (parallel):   UI wiring    ‖  Mobile PWA
Layer 4 (sequential): Security + Testing + Deploy
```

### Opening Parallel Threads in Replit Agent 4

```
How to run 3 agents at once in Replit:
1. Click the "+" button to open a new Agent chat thread
2. Give each thread a label (Thread A: Backend, Thread B: Frontend)
3. Paste Prompt 1A into Thread A, Prompt 1B into Thread B simultaneously
4. Monitor the Kanban board — both threads show active tasks
5. When both complete, start the next parallel layer

Warning: threads share the same filesystem. Avoid having two threads
edit the SAME file at the same time. Structure prompts so each thread
owns distinct files/folders.
```

### File Ownership Rules (prevent conflicts)

Assign each parallel thread exclusive ownership of specific directories:

```
Thread A (Backend)  → /server/routes/, /server/middleware/, /server/db.ts
Thread B (Frontend) → /client/src/pages/, /client/src/components/
Thread C (Agents)   → /server/agents/, /server/orchestrator.ts
Thread D (Shared)   → /shared/ (only touch between parallel rounds)
```

## SECTION 3 — The 24-Hour Hackathon Sprint Framework

### Time Budget Template

```
Hour 00:00–00:30  [BOOTSTRAP]     Sequential. DB schema + project init.
Hour 00:30–04:00  [FOUNDATION]    Parallel. Backend API + Frontend shell.
Hour 04:00–10:00  [CORE LOGIC]    Parallel. Main features + AI/data layer.
Hour 10:00–16:00  [INTEGRATION]   Parallel. Wire UI to backend + mobile.
Hour 16:00–18:00  [HARDENING]     Sequential. Security + error handling.
Hour 18:00–20:00  [TESTING]       Sequential. E2E test run + bug fixes.
Hour 20:00–23:00  [POLISH]        Sequential. UI/UX + deploy to prod.
Hour 23:00–23:45  [STORY]         Record demo video + write submission.
Hour 23:45–24:00  [SUBMIT]        Submit. Don't touch code after this.
```

### The Checkpoint System

Every 2 hours, do a mandatory 10-minute checkpoint:

```
Checkpoint checklist:
□ Is the app still running? (check browser + server logs)
□ Can I create/read the core data entity? (manual test)
□ Are all DB migrations applied? (check table list)
□ Do I have a working deploy URL? (even if incomplete)
□ Have I committed / hit a save checkpoint in Replit?
□ Am I on track for the sprint timeline?

If you find a broken state during a checkpoint:
→ Do NOT try to fix it by prompting the agent randomly.
→ Rollback to the last working checkpoint first.
→ Then write a precise diagnostic prompt (see Section 5).
```

### What to Cut When Behind Schedule

If you're running 2+ hours behind, cut in this order (least to most painful):

```
1. Mobile PWA / responsive polish     → Cut first. Core dashboard still scores.
2. Advanced data visualizations        → Replace with a simple table.
3. Third AI agent (if you have 3)      → Reduce to 2 agents.
4. Email/social asset generation       → Keep competitor + positioning only.
5. Admin / settings pages              → Judges won't see these anyway.

Never cut:
✗ Core user flow (sign in → create → see results)
✗ Human approval gate (judges look for this)
✗ Demo-ability (app must work during video recording)
✗ Production deploy URL (submission requires a live link)
```

## SECTION 4 — Stack Decisions & Replit-Native Patterns

### The Zero-Setup Stack (optimized for 24h builds)

```
Auth:       Replit Auth (OIDC) — 0 config, just works
Database:   Replit built-in PostgreSQL + Drizzle ORM
Backend:    Express.js + TypeScript
Frontend:   React + Vite + Tailwind CSS
AI:         Anthropic SDK (@anthropic-ai/sdk)
State:      TanStack Query (server state) + useState (UI state)
Realtime:   Server-Sent Events (simpler than WebSockets, built into HTTP)
Deploy:     Replit Deployments (autoscale) — one command
```

### Replit-Specific Prompt Patterns

**Triggering zero-setup infrastructure:**
```
Use Replit's built-in PostgreSQL (DATABASE_URL is already set in env).
Use Replit Auth for authentication (REPL_ID and REPLIT_DB_URL are available).
Do NOT install or configure any external database or auth service.
All secrets are in Replit's Secrets panel — read them via process.env.
```

**Triggering parallel agents:**
```
I want you to create [Task A] in one agent thread while I start
[Task B] in a separate thread. Structure your output so it does
NOT touch /client/ — I will handle that in the other thread.
```

**Using the Infinite Canvas:**
```
Open the Infinite Canvas. I want to review the visual layout of
[page name] at 1440px, 1024px, and 375px widths. Identify any
overflow, truncation, or alignment issues. Fix them by adjusting
Tailwind classes — do NOT change any JavaScript logic.
```

**Triggering web search in agents:**
```
Use the web_search tool to research [topic] in real time.
Do not rely on your training data for competitor pricing or
current market information — search for fresh data.
```

### AI Model Selection Guide

```
Task                              → Best Model
─────────────────────────────────────────────────
Competitor research (needs web)   → claude-sonnet-4-20250514 + web_search tool
```

## SECTION 5 — Debugging Agent-Generated Code

### Diagnostic Prompt (use when something is broken)

Never prompt the agent with "fix it" or "it's not working". Always diagnose first:

```
The app has an error. Before fixing anything, help me diagnose it.

SYMPTOM: [Exact error message or behavior]
LOCATION: [Which page / which API endpoint / which function]
LAST WORKING STATE: [What was true before this broke]
RECENT CHANGES: [What the agent last modified]

Step 1: Read these files and identify what's wrong:
  [list the relevant files]

Step 2: Explain the root cause in plain English before writing any code.

Step 3: Propose one surgical fix. Do not refactor anything else.
Do not change any files not directly related to this error.
```

### Common Agent Failure Patterns & Fixes

**Agent generated code that doesn't match the schema:**
```
The agent wrote code referencing columns that don't exist. 
Read /shared/schema.ts first. Then re-read the file you just wrote.
List every column reference and verify each one exists in the schema.
Fix any mismatches. Do not change the schema — change the code.
```

**Agent used a library that isn't installed:**
```
You referenced [library] but it's not in package.json.
Either: (a) install it with npm install [library], or
(b) rewrite the code using only already-installed packages.
Show me package.json first, then make your decision.
```

**Agent broke a working feature while building a new one:**
```
The feature you added broke [existing feature].
Roll back ONLY the changes to [filename] using git diff or
by re-reading the file and reverting to the last working version.
Do NOT touch [the new feature file] — that part is correct.
```

**Agent keeps hallucinating API endpoints:**
```
Stop. Read /server/routes/ and list every registered endpoint.
Do not assume any endpoint exists that you don't see in those files.
Now re-read my original request and complete it using only
real endpoints from that list.
```

**Agent generates invalid JSON from AI model calls:**
```
The JSON parsing is failing because the AI response contains
markdown code fences or extra text. Fix the parsing like this:

  const raw = response.content[0].text;
  const cleaned = raw.replace(/```json\n?/g, "").replace(/```/g, "").trim();
  const parsed = JSON.parse(cleaned);

Also add a try/catch around the JSON.parse. On parse failure,
log the raw response and set status to "error".
```

## SECTION 6 — Judging Criteria Optimization

Most hackathon judges score on three axes. Here's how to optimize each:

### Progress / Delta (How much was built in the time window)

The judges compare your starting state to your ending state.

```
Maximize Delta by:
→ Starting from zero (blank project) not a template
→ Using parallel agents to multiply output volume
→ Recording your starting state (screenshot/git commit at Hour 0)
→ Showing the Kanban board in your demo — live proof of parallel work
→ Stating the delta explicitly: "We built X, Y, Z in 24 hours"

Prompt to maximize delta signal:
"The Replit Kanban board shows 3 agents working in parallel. 
 Make sure the board is visible and updating during the demo recording.
 Each agent card should show real-time status transitions."
```

### Execution Quality (Does it actually work?)

```
Zero broken states in your demo. Achieve this by:
→ Testing the exact demo flow 3 times before recording
→ Using skeleton loaders so there's never a blank/broken moment
→ Adding React ErrorBoundary to all pages
→ Having a fallback for each AI call (if agent fails, show cached example data)

Prompt for zero broken states:
"Add a React ErrorBoundary wrapping all route components.
 Fallback UI: a slate-800 card with '⚠️ Something went wrong' and a 
 retry button. This must never show a white screen or console error
 during a demo."
```

### Story / Impact (Why does this matter?)

```
The story must answer three questions:
→ Who is suffering? (specific person, not "businesses")
→ What is the exact pain? (quantified if possible)
→ How does your product fix it right now, today?

Demo video structure (3 minutes max):
  0:00–0:30  Show the pain (messy spreadsheet, wasted hours)
  0:30–2:00  Show your product solving it live (real data, real agents)
  2:00–2:30  Show the safety/trust feature (human approval gate)
  2:30–2:50  Show mobile experience
  2:50–3:00  "What used to take 3 weeks, takes 3 minutes."

Prompt for story-ready output:
"In the app, add a dashboard metric row showing:
 'Time saved vs manual: ~18 hours' | 'Agents run: 3' | 'Assets generated: 5'
 These stats should be prominent — first thing judges see after login."
```

## SECTION 7 — Security & Production Readiness

### The Human-in-the-Loop Pattern (Required for Agent Apps)

Any app where AI takes actions needs explicit human approval gates:

```typescript
// Pattern: never let AI agents deploy/send/publish autonomously
// Always require human confirmation before consequential actions

// ❌ Wrong — agent deploys directly
await runMarketingAgent(projectId);
await deployToProduction(projectId); // NO! Agent chose this

// ✅ Right — human approves before deployment
await runMarketingAgent(projectId);
// Status → "awaiting_approval"
// UI shows approval modal
// Human types "APPROVE"
// THEN: deployToProduction(projectId)
```

**Prompt for human-in-the-loop:**
```
The AI agents must NEVER autonomously send emails, publish content,
charge payment methods, or modify production data. 

After all agents complete, set status to "awaiting_approval".
Show a modal requiring the user to explicitly confirm before any
deployment action. The confirmation must require typing "APPROVE" —
not just clicking OK. This is a non-negotiable security requirement.
```

### Environment & Secrets Checklist

```
Before submitting/deploying, verify:
□ No API keys hardcoded in any source file
□ All secrets in Replit Secrets panel (or .env not committed)
□ ANTHROPIC_API_KEY is set in Secrets, not in code
□ DATABASE_URL is from environment, not hardcoded
□ NODE_ENV=production is set for the deployed environment
□ /health endpoint exists and returns 200

Prompt to audit secrets:
"Scan all files in /server and /client for hardcoded strings that 
 look like API keys, passwords, or tokens (patterns: sk-, Bearer, 
 secret, password=). List any you find. Do not fix them yet — 
 just list them so I can move them to environment variables."
```

## SECTION 8 — Reference: Prompt Quality Checklist

Before pasting any prompt to your agent, verify:

```
□ Role is defined ("You are building X for project Y")
□ Existing context is described (stack, files already created)
□ Task is specific (exact file paths, function names, endpoint paths)
□ Data shapes are defined (what goes in, what comes out)
□ Constraints are listed (what NOT to do, what NOT to touch)
□ Acceptance criteria are testable ("show me the terminal output")
□ Error handling is specified for async/background tasks
□ No ambiguous words: "good", "proper", "nice", "clean" (be specific)
□ Parallel thread boundary is clear (which files this thread owns)
□ Length is appropriate (complex tasks deserve longer prompts)
```
